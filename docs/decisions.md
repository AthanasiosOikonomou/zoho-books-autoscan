# Decisions

| Date | Decision | Why |
|---|---|---|
| 2026-11-03 | Rebuild on Catalyst (Node.js), not repair the Deluge function | Deluge runtime caps, single-page inbox read, no state; see architecture.md |
| 2026-11-03 | Claude Haiku (cost-first); Sonnet only as an explicit config switch | ~$0.001/invoice; golden-set test decides if a stronger model is ever needed |
| 2026-11-03 | Dedupe on vendor + supplier invoice number, never on "PO already has a bill" | One PO is billed by several supplier invoices (partial deliveries) |
| 2026-11-03 | Exceptions stay in the Books inbox; state lives in Catalyst Data Store; new docs always processed before retries | The queue behaviour the client requires in writing; no undocumented folder-move API |
| 2026-11-03 | Build and test in the Books sandbox org + Catalyst Development env; the client disables the old scheduler at UAT | Client instruction |
| 2026-11-03 | Token scope `ZohoBooks.fullaccess.all`; read-only protection via the Books user role, not the scope | Documents API has no granular scope |
| 2026-11-03 | Phase 1 also matches the invoice against the PO's remaining value | Lets the closing invoice of a manually part-billed PO auto-match |
| 2026-11-04 | ROWIDs are never taken from insert/update responses; re-read through ZCQL after every insert, every update response verified | ROWIDs are 17 digits (> 2^53); the REST responses carry them as JSON numbers, so `JSON.parse` rounds them and updates hit the wrong row or none |
| 2026-11-04 | `PROCESSING` claims older than `LOCK_STALE_MINUTES` are retry candidates; `AI_ERROR` / `BOOKS_ERROR` / `ATTACH_FAILED` retry on the next run | A dead run must not park documents for 12 h; service errors are not the finance team's problem |
| 2026-11-04 | Total tolerance is £1 on the invoice total (was 2p) | Client rule |
| 2026-11-04 | The bill carries the supplier invoice total, not the PO's: the difference inside the tolerance is posted as the bill's `adjustment`; a bill whose total still differs is reported with a note | Client rule — the previous implementation billed the PO value |
| 2026-11-04 | Credit notes get their own reason `CREDIT_NOTE` (manual for now) | Suppliers send credit notes, sometimes tied to a bill, always with the PO number; automation is a later phase |
| 2026-11-04 | Reconciliation window: exceptions re-checked every 6 h for up to 28 attempts (a week), reusing the stored extraction | A PO fixed hours or days later must bill itself without raising the AI cost |
| 2026-11-04 | Credit notes → Books vendor credits: lines by MPN against the PO, total verified (draft deleted on mismatch), applied to the bill named on the note or the PO's single bill, else PO only + report line | Client rule; a credit must never sit outside Books |
| 2026-11-04 | One digest email per local day, sent by the first run after `DAILY_REPORT_HOUR`; per-run reports stay in the log | Finance asked for one readable end-of-day email, not one per run |
| 2026-11-05 | Line matching keys: the item custom field "Supplier Reference" on the PO line first, then item MPN, SKU, item code — all compared with case, spaces, dots, dashes and slashes removed | Production POs print both Supplier Reference and MPN; suppliers print their own code, sometimes with different punctuation (`ZK410-KIT` vs `ZK410KIT`) |
| 2026-11-05 | Vendor carriage rule and tolerance are read by field *label*, not API name | Sandbox custom fields are named `cf__sb_<org>_…`, production `cf_…` |
| 2026-11-05 | Phase 2 bills carry the invoice: invoiced quantities, invoice unit prices (within tolerance, or lower when accepted), invoice carriage; a PO with no coded lines falls back to the total match | Client rule "bill = invoice"; partial deliveries are routine; many items still lack a Supplier Reference / MPN |
| 2026-11-05 | `reason_code` / `reason_text` are written as `''` when a document reaches a clean status | Data Store partial updates leave absent columns untouched, so a BILLED row kept the reason of its last failed attempt |
| 2026-11-05 | Price policy stays configurable (`LINE_PRICE_TOLERANCE_PCT`, `ACCEPT_LOWER_PRICE`) with placeholder values until the client answers | Asked by email on 5 Nov; changing the policy is an env change, not a release |
| 2026-11-06 | Line price policy: up to 5 % **below** the PO unit price → billed at the invoice price (noted); any increase, or more than 5 % below → `PRICE_MISMATCH`. `ACCEPT_LOWER_PRICE` removed; `LINE_PRICE_TOLERANCE_UP_PCT` (0) and a 1p rounding guard added | Client decision 6 Nov 2026 ("5 % tolerance only for items lower in cost, no higher; within it create the bill at the supplier invoice price") |
| 2026-11-06 | Purchase orders created by the web shop get no special carriage handling | Client decision 6 Nov 2026: all POs treated the same; the vendor-level carriage rule is the only rule |
| 2026-11-06 | `SCAN_SINCE`: inbox documents created before the configured date are never read, recorded or reported; an unparsable creation time is treated as old (skipped, warned) | Client: the historical backlog (~7k files) must not be touched; without a cutoff the first production run would start on the oldest documents |
| 2026-11-06 | No MPN readiness list; handover documentation after UAT | Client: they know which items lack codes and update them themselves; UAT may change behaviour |
| 2026-11-06 | Report transport = SMTP from a mailbox the client owns (plain login password accepted; app password only if 2FA is enabled) | Catalyst Mail needs domain verification the client won't do; the mailbox is theirs, so the credential lives with them |
| 2026-11-10 | One variable set for both Catalyst environments; the profile (sandbox / production) comes from the environment Catalyst reports at run time; production reads `PROD_<NAME>` overrides and never inherits `BOOKS_ORG_ID`, `BOOKS_APP_BASE`, `DRY_RUN`, `SCAN_SINCE`, `CARRIAGE_ITEM_ID`; it refuses to start without `PROD_BOOKS_ORG_ID` / `PROD_SCAN_SINCE` or against the sandbox organisation | Production is deployed from the Console, not the CLI, and how variables travel with that deployment is not documented — identical variables everywhere removes the question; the tolerances under test are guaranteed to be the ones that go live; a copied `DRY_RUN=false` can never reach production |
| 2026-11-10 | Invoice carriage on a PO without a carriage line is booked on `CARRIAGE_ITEM_ID` if the organisation has one carriage item, else on `CARRIAGE_ACCOUNT_ID` (the freight purchase account), else on the first line's account | Production keeps ~65 carriage items, one per supplier or brand (several per supplier), all posting to one freight account — picking "the supplier's item" is ambiguous, the account is not |
| 2026-11-13 | The model copies, the code computes: delivery-type charges are returned one by one (`charges`) and summed in code; the invoice date is also returned as printed (`invoice_date_raw`) and converted in code, day first | On a second set of real documents the model added 14.95 + 1.38 to 16.52 and wrote 01.10.2026 as 2026-01-10 (both with a note admitting it). Arithmetic and date conversion are deterministic now; the model's own values are only the fallback |
| 2026-11-13 | Pack ↔ each: same code, the invoice line total is a whole number of PO units to the penny, quantities differ by a whole factor ≥ 2 and the PO still has those units → billed in PO units, noted in the report | Suppliers invoice single units (6 EACH × 184.71) where the PO line is a pack (1 × 1108.26). Anything else keeps the plain reading (`QTY_EXCEEDS` / `PRICE_MISMATCH`) |
| 2026-11-13 | The unit price comes from the line total when the printed price does not multiply up to it (or is missing); rows printed at 0.00 are noted and skipped | Prices quoted per litre / per 100 / before a line discount; courier names printed as zero-value rows |
| 2026-11-13 | A surcharge printed as a coded row of the product table is a charge (carriage), not a product line; a value in the customer's PO format under a bare "Order No" label is the PO reference | Real layouts; a surcharge row read as a product line could never match a PO line |
| 2026-11-13 | The item MPN is read from `part_number` (the API name of the Books "MPN" field); a non-scalar `item_code` is ignored | `item.mpn` does not exist in the API, so the MPN fallback never matched; one organisation returns `item_code` as `{}` |
| 2026-11-13 | Payment terms: when no term has the PO's (days, label) pair but the label names exactly one term of the organisation, the bill uses that term's number | Books returns special terms ("Due end of next month", defined as −3) on a PO as 0 days + the label; sending 0 would make the bill due on receipt |
| 2026-11-13 | `scripts/replicate.js` (pull read-only → check offline → push to the sandbox → verify) is the way to test a new batch of real documents | Rebuilds the POs behind real invoices in the sandbox with their own numbers; the snapshot lives in the git-ignored documents folder |
| 2026-11-16 | Carriage at or below the PO's carriage is accepted under every vendor rule and billed as invoiced on the PO's carriage line for its whole open quantity (the line and the PO complete); no carriage invoiced → the line stays open (PO partially billed) and a later carriage-only invoice bills it; the vendor rule decides only about carriage **above** the PO (`CARRIAGE_BELOW_PO_OK`, default true) | Client decision 16 Nov 2026: a lower carriage figure should be billed and the PO completed; a missing one is invoiced separately later. PO carriage is compared on what is still open, so a second part-shipment charging carriage again is "above the PO" |
| 2026-11-16 | A product surcharge ("PRODUCT SURCHARGE 5%", "Order Surcharge") is part of the product price, not carriage: spread over the product lines by value before the price check (`SURCHARGE_IN_PRICE`, default true). Classified in code from the printed description of each charge — surcharge / levy without a delivery word; "fuel surcharge" stays carriage | Client decision 16 Nov 2026: surcharges are worked into the PO's item prices, so the invoice must still match; where the PO price does not contain it the document goes to review as a price increase. Classifying in code leaves the prompt — and every stored extraction — untouched |
| 2026-11-16 | Value fallback for items without a supplier code: one open PO line without Supplier Reference / MPN, same unit price (or the same money as a whole pack), enough open quantity, not claimable by another invoice line, descriptions share a word → matched and noted with the code to add; otherwise `LINE_UNMATCHED` (`LINE_VALUE_FALLBACK`, default true) | Client asked for a fallback on description / value / line total; a description alone is never a key for money, a unique value is. A PO line that has a supplier code is matched by it or not at all |
| 2026-11-16 | Notes of a clean outcome are stored in `reason_text` (with an empty `reason_code`) and shown under the bill in the daily digest | The digest reads the state table, not the run: "matched by value — add this code to the item", "billed below the PO price", "carriage left open" never reached finance otherwise. No new column, so no Data Store change in either environment |
| 2026-11-16 | A prompt change also re-reads documents parked for a matching reason (`LINE_UNMATCHED`, `CARRIAGE_MISMATCH`, `PRICE_MISMATCH`, `QTY_EXCEEDS`, `TOTAL_MISMATCH`), once | A misread line, quantity, price or charge surfaces as exactly these reasons; without it a parked document keeps its old reading for the whole reconciliation window. One AI call per parked document per prompt change (≈ $0.001 each, capped by `MAX_RETRY_PER_RUN`) |
